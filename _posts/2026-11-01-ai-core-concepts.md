## 一、LLM：一切的地基

+ **LLM = Large Language Model**，大语言模型，简称"大模型"
+ 底层引擎是 **Transformer 架构**：Google 团队 2017 年提出，论文《Attention Is All You Need》
+ Google 发明了火种，OpenAI 把它点燃：
    - 2022 年底 **GPT-3.5** 横空出世，第一个真正可用级别的大模型
    - 2023 年 3 月 **GPT-4** 发布，把 AI 能力天花板拉到新高度

## 二、大模型怎么工作：文字接龙

大模型的本质非常朴素——**文字接龙**游戏：

1. 输入"这篇文章写的怎么样？" → 模型预测下一个概率最高的词："特别"
2. 把"特别"抓回来追加到输入后面 → 再预测下一个字："的" → 再塞回去 → 预测"棒"
3. 模型发现话说完了，输出一个**特殊的结束标识符**，回答结束
4. 最终拿到完整回答："特别的棒"

这解释了为什么大模型总是**一个词一个词地往外蹦**——它就是这么运作的。

### 推理模型 / Extended Thinking

+ 上面说的"接龙"是**瞬时输出**；推理模型（OpenAI o 系列、DeepSeek-R1 等）会在给出答案前先生成一段**内部思考**（thinking），想清楚再答
+ 本质是**测试时计算**（test-time compute）：用推理阶段更多的算力换更高质量的输出，思考量可通过 **thinking budget / reasoning effort** 调节
+ Agent 场景下的形态：**interleaved thinking**——每步工具调用之间都插一次思考（见第十四节）

## 三、Tokenizer

大模型本质是一个庞大的**数学函数**，里面全是矩阵运算：接收数字、输出数字，不认识人类文字。所以中间必须有个"翻译"——**Tokenizer**：

| 环节 | 方向 | 步骤 |
| --- | --- | --- |
| **编码** | 文字 → 数字 | 两步：切分 + 映射 |
| **解码** | 数字 → 文字 | 一步：映射（无需切分，模型每次只吐一个 Token） |

编码两步拆解：

1. **切分**：把输入拆成最小片段，每个片段就是一个 **Token**
2. **映射**：每个 Token 对应一个数字，即 **Token ID**（一对一绑定，本质是同一东西的两种表达）

完整流程：`文字 → Token 列表 → Token ID 列表 → 模型运算 → 输出 Token ID → 解码回 Token`

## 四、Token：词元

**Token 才是大模型处理文本的基本单元**：一个 Token 一个 Token 地接收输入，一个 Token 一个 Token 地输出结果。

+ "程序员" → 被拆成"程序" + "员" 两个 Token
+ 英文常见词 `hello`、`going` 各是一个 Token；但 `helpful` → `help` + `ful`
+ 极端情况：一个字符（✓）需要 3 个 Token 来表示

**Token 是模型自己学会的一套文本切分规则**，切出来的每一块就是它一次能处理的最小单位。

换算参考：

| 换算 | 数值 |
| --- | --- |
| 1 Token ≈ | 0.75 个英文单词 |
| 1 Token ≈ | 1.5 ~ 2 个汉字 |
| 40 万 Token ≈ | 60 ~ 80 万汉字，或 30 万英文单词 |

## 五、Context：上下文

大模型只是数学函数（输入 → 输出），并不真的有记忆，而是每次发消息时，背后的程序会自动把**整段对话历史**找出来，和问题一起发过去。

**Context（上下文）= 大模型每次处理任务时接收到的信息总和**，包含：

+ 用户问题、对话历史
+ 模型正在输出的每一个 Token（会被追加进来）
+ 工具列表、System Prompt 等

可以把它看成大模型的**临时记忆体**。

## 六、Context Window：上下文窗口

Context Window = Context 能容纳的最大 Token 数量。


## 七、Context Engineering：上下文工程

Prompt Engineering "凉了"之后，2026 的正统接班人是 **Context Engineering**：

|      | Prompt Engineering | Context Engineering                                              |
| ---- | ------------------ | ---------------------------------------------------------------- |
| 优化对象 | 那一句指令怎么措辞          | **每一轮塞进窗口的整个 token 载荷**（system prompt + 工具定义 + 工具结果 + 检索文档 + 记忆） |
| 时机   | 设计时写好就完了           | **运行时逐轮管理**                                                      |
| 核心问题 | "这话怎么写？"           | "模型此刻需要哪些信息？"                                                    |

三大杠杆：

1. **压缩（Compaction）**：长对话/长任务跑不下了，把历史**摘要瘦身**——保留关键决策、文件路径、待办事项，丢掉冗余过程
2. **子代理上下文隔离**：把工具密集的活派给 Sub-agent（见第十五节），让它在自己的窗口里烧 token，只把结论带回主窗口
3. **结构化记忆**：把关键事实写进笔记文件（`MEMORY.md` / `AGENTS.md`），跨轮、跨会话取用（见第八节）

配套技巧 **Prompt Caching**：把稳定不变的上下文前缀缓存起来，省费用、降延迟（也有"缓存全量"反而比"摘要瘦身"划算的场景——是个权衡）。

## 八、长期记忆 Memory：持久化

Context 是**临时**记忆体——会话结束就没了。2026 的补齐方向是**持久记忆**，三层模型：

| 层 | 内容 | 类比 |
| --- | --- | --- |
| 情景记忆（episodic） | 本次会话发生了什么 | 今天的经历 |
| 语义记忆（semantic） | 长期事实与偏好 | 我知道的常识、用户的习惯 |
| 程序记忆（procedural） | 做事的方法、流程 | 会用的技能 |

落地形态（都很朴素）：

+ **memory tool**：模型自己读写的记忆文件（Claude 等已内置，可搜索历史对话、导入导出记忆）
+ **`AGENTS.md`**：项目级持久上下文，已是 **6 万+ 开源项目采用的"给 Agent 的 README"**，Claude Code / Cursor / Copilot 等都支持
+ **`MEMORY.md` 式索引文件** + 记忆 MCP server（claude-mem、Hindsight 等插件）

2026 的一个反直觉共识：**文件式的朴素记忆在实际采用上跑赢了重型 RAG 方案**——纯文本可读、可改、可版本控制。

## 九、RAG

场景：上千页的公司产品手册，要让大模型据此回答用户问题。

+ 整本跟着问题一起发过去？→ **不可行**：窗口可能撑爆，成本也失控
+ 解法 **RAG（检索增强生成）**：先从手册中**抽取与问题最匹配的几个片段**，只把片段发给模型

效果：模型接到的不是一整本书而是几段话 → 不受 Context Window 限制，成本低很多。

## 十、Prompt：提示词

**Prompt = 给大模型的具体问题或指令**（比如"帮我写一首诗"）。别想得太高端，就是一句话输入。

+ Prompt 太模糊 → 输出不可控（可能给你古诗、现代诗甚至打油诗）
+ 好的 Prompt：**清晰、具体、明确**（如"写一首五言绝句，主题秋天的落叶，风格悲凉"）
+ **Prompt Engineering**：研究怎么把话说清楚。如今热度大减——门槛太低 + 模型能力强到能猜出模糊意图；它的"接班人"是 Context Engineering（第七节）

### User Prompt vs System Prompt

有些时候不仅要告诉模型任务，还要告诉它**人设和规则**（"它是谁""按什么规则做事"）：

| | User Prompt（用户提示词） | System Prompt（系统提示词） |
| --- | --- | --- |
| 作用 | 说明**具体任务** | 说明**人设和做事规则** |
| 来源 | 用户在对话框直接输入 | 开发者在**后台配置**，用户看不到 |
| 影响 | 决定这次回答什么 | 一直影响模型行为 |

例子——数学辅导机器人：

+ System Prompt（后台）："你是耐心的数学老师，不要直接给答案，要一步步引导学生思考"
+ User Prompt（对话框）："3+5 等于几"
+ 结果：模型不答"8"，而是引导——"你手里有 3 个苹果，又拿了 5 个，一共多少个？数数看"

没有 System Prompt 会直接说 8；有了它，模型守住规矩、又完成具体需求。

## 十一、Tool：工具

大模型的弱点：**无法感知外界环境**——问"今天上海天气怎么样"，它只能答"知识库截止到某年某月"。

解法是 **Tool（工具）**，本质就是一个**函数**：给输入、给输出。

+ 例：天气查询工具 = 输入（城市 + 日期）→ 内部调气象局接口 → 输出（天气信息）

### 一次工具调用的完整流程（四个角色）

角色：**用户、大模型、工具、平台**。平台是"传话筒"——前三个角色没法直接对话，靠它上传下达，本质是一段代码。

1. 用户问题 → 发给**平台** → 平台转发给**大模型**（附带**可用工具列表**：天气、计算器……）
2. 大模型分析后生成"**调用某工具**"的指令文本（工具名 + 参数）→ 发给平台。注意：**模型无法自己调工具，它唯一的能力就是输出文本**
3. **平台**真正执行函数调用 → 拿到工具结果 → 返回给大模型
4. 大模型把结果整理成人话 → 平台转发给用户

### 角色分工（高频误区：到底是谁在调工具）

| 角色 | 职责 |
| --- | --- |
| 大模型 | ① 选择工具并生成参数；② 拿到结果后归纳总结 |
| 工具 | 执行具体动作（查天气） |
| 平台 | 串联全流程：传工具列表、根据指令真正调工具、转发信息 |

误区 ：以为调工具的是模型。模型只能输出文本表达"我想调什么"，真正调用工具的是平台。
Tool 的本质 = 给大模型提供一套可调用的外部能力，让它能**感知和影响外部环境**。

### Computer Use / Browser Use：第四种"工具"

预定义函数之外的新路：模型直接**看截图 → 移动鼠标 → 点击 → 敲键盘**，像人一样操作真实 GUI。

+ 意义：没有 API 的老系统、桌面软件也能被 Agent 驱动——是"真能干活"的助理类产品的核心底座
+ 对白帽：这也是**全新攻击面**（GUI 自动化代理的权限与越界）

## 十二、MCP：协议

上一节的流程有个工程大问题：平台要把工具列表传给模型、还要能调工具 → 工具必须先"接入"平台。而**每个平台的接入规范都不一样**：

+ 用 ChatGPT → 按 OpenAI 规范写一套
+ 用 Claude → 按 Anthropic 规范写一套
+ 用 Gemini → 按 Google 规范写一套

同一个工具要写 3 遍。于是有了 **MCP（Model Context Protocol，模型上下文协议）= 统一的工具接入标准**。

价值：工具按 MCP 规范开发**一次**，所有支持 MCP 的平台都能用——就像所有手机统一 Type-C 接口。

## 十三、MCP v2 与协议生态

+ **无状态协议核心**：会话状态下沉，MCP server 可以像 Web 服务一样水平扩展、缓存、路由
+ **扩展框架**（extensions）：协议功能有了正式的生命周期与废弃流程——Roots / Sampling / Logging 已进入废弃流程
+ **官方 Registry**（注册中心）+ **OAuth** 鉴权：工具的分发与安全接入规范化
+ **Elicitation**：服务器可以**反向**向用户请求输入（Agent 流程不再是单向的）
+ **工具延迟加载 / Tool Search**：工具太多塞不下窗口时，先给模型一个"搜索工具"的元工具，按需再加载详情——省 token（ZCode 的 LocalToolSearch 就是这个模式）
+ **代码执行替代一对一调用**：把 MCP 工具暴露成代码 API，模型写一段代码一次串起 N 个工具调用——Agent 调工具的方式正在从"逐个指令"变成"写代码编排"

### 协议格局：MCP 之外还有 A2A

| 协议 | 管什么 |
| --- | --- |
| **MCP** | agent ↔ 工具 / 上下文 |
| **A2A**（Agent-to-Agent，Google 发起，现归 Linux 基金会） | agent ↔ agent：跨平台发现、任务委派、事务协作，150+ 组织、已进主流云平台 |
| ACP / UCP | 同场竞技的其他互操作协议 |

2026共识：**先 MCP 后 A2A**——先给 agent 接上工具，需要跨厂商/跨组织协作时再加 A2A。

## 十四、Agent：多步自主调用工具

有了 Tool + MCP 还不够。更难的任务："今天天气怎么样？**如果下雨**，帮我查附近有没有卖雨伞的店"——需要**多轮**工具调用（定位 → 天气 → 店铺）：

1. 模型思考：查天气要先知道位置 → 调用**定位工具** → 返回经纬度
2. 再思考：拿着经纬度查天气 → 调用**天气工具** → 返回"下雨"
3. 再思考：下雨 → 按用户要求找伞店 → 调用**店铺工具** → 返回"100 米内全家便利店"
4. 综合所有信息 → 给出最终答案

这不再是单次工具调用：模型要**一步一步思考当前情况、决定下一步做什么**，具备了自主规划能力。

> **Agent = 能自主规划、自主调用工具、持续运作直至完成用户任务的系统。**

+ 流行产品：Claude Code、Codex、Gemini CLI
+ 经典构建模式：ReAct、Plan and Execute

## 十五、Sub-agent 与 Agent Teams

+ **Sub-agent（子代理）**：主 Agent 派生出一个**独立上下文窗口**的子实例，可配独立的工具、模型、权限，并行干活，**只把结论回传主窗口**——既是并行加速，也是第七节说的上下文隔离手段
+ **Agent Teams（智能体团队）**：多个 teammate 会话互相发消息协作，由 lead 统一调度（Claude Code 已内置）

配套的全家桶（以 Claude Code 为例）：

| 组件 | 作用 |
| --- | --- |
| **Hooks** | 生命周期钩子：在工具调用前后、子代理派生等事件上挂**确定性脚本**拦截/增强行为 |
| **Plugins** | 把 skills / MCP / hooks / subagents **打包分发**的封装层（不是新原语，是包装） |
| **Workflows** | 把"计划"从模型脑子里搬进脚本，减少自由发挥 |

和 Agent Skill 的关系：Skill 管单个技能怎么做事；Hooks 管行为拦截；Plugins 管打包分发——一件套一层。

## 十六、Agent Skill：Agent的说明文档

新痛点：想让 Agent 按你的私人规则做事（出门习惯：下雨带伞、光照强戴帽、空气差戴口罩、风大穿防风外套、手机必带 + 固定输出格式），就必须每次把一大串规则**复制粘贴进 Prompt**——反人类。

解法：**Agent Skill = 提前写好给 Agent 的一份说明文档**（Markdown），结构分两层：

1. **元数据层**（相当于封面）：至少要有 `name`（技能名）和 `description`（描述）两个属性
2. **指令层**：格式不限，说明白即可——目标、执行步骤、判断规则、输出格式、示例

```markdown
---
name: go-out-checklist
description: 出门前查天气并按个人习惯生成携带物品清单
---

## 目标
出门前根据天气给出携带物品建议

## 执行步骤
1. 调用定位工具获取经纬度
2. 调用天气工具获取天气
3. 按判断规则整理物品清单，严格按输出格式回复

## 判断规则
下雨带伞 / 光照强戴帽 / 空气差戴口罩 / 风大穿防风外套 / 手机必带

## 输出格式
先一句总结，再列物品清单
```

### 存放规范（以 Claude Code 为例）

```text
~/.claude/skills/<skill 名>/SKILL.md
```

两条硬性规定（"接头暗号"，写错系统不认）：

1. 在 `.claude/skills` 下新建**文件夹**，文件夹名必须与 skill 的 `name` 相同（如 `go-out-checklist`）
2. 文件夹里的文件名必须是 **`SKILL.md`**（SKILL 全大写）

### 加载与执行机制（渐进式披露）

+ **启动时**：Claude Code 扫描 skills 目录，只读每个 skill 的**元数据层**（name + description）——指令层可能很大，暂不读
+ **提问时**：用户问题与某 skill 的名称/描述**相关**，才读取它的指令层 → 节省 Token
+ 演示流程：识别相关 → 读全文 → 调定位工具 → 调天气工具 → 严格按 skill 规定格式输出
+ （演示中的定位/天气工具是提前做成的 **MCP 工具**，`/mcp` 可验证）

Agent Skill 还有高级功能：运行代码、引用资源等，渐进式披露机制是一大特色。

**`AGENTS.md` 与 Agent Skill 是互补关系**——AGENTS.md 是项目级、仓库范围的持久规则，Agent Skill 是单个可触发的技能；前者管"在这个项目里怎么做人"，后者管"这件事怎么做"。

## 十七、Agent 安全：新的漏洞面

Agent 有了自主性 + 外部输入（网页、文档、工具返回值），就出现了传统 Web 没有的漏洞类：

+ **间接提示注入（Indirect Prompt Injection）**：恶意指令**藏在 Agent 检索的内容里**（网页、文档、邮件、代码注释、工具返回值），Agent 读了就被劫持。2026 已被当成**一等漏洞类**，业界共识是要**架构级缓解**（权限隔离、来源标注），光靠提示词加固没用；CrowdStrike 的注入技术分类已扩到 200+
+ **Skill / 工具供应链**：Snyk "ToxicSkills" 研究发现 **36% 的公开 agent skill 含安全缺陷**，ClawHub 等技能市场出现伪装成正常技能的恶意 skill——生态把 skill 定性为"**新的 CI/CD 供应链**"；对应还有 **tool poisoning**（工具描述里藏指令）
+ **框架**：OWASP LLM Top 10（LLM01 即提示注入）+ OWASP Agentic AI Top 10；自主性靠 **permission modes / sandboxing** 做安全阀

## 十八、概念总结

| 概念                          | 一句话定义                                                            |
| --------------------------- | ---------------------------------------------------------------- |
| **LLM**                     | 大模型，所有 AI 技术的核心                                                  |
| **Token**                   | 大模型处理数据的最基本单元                                                    |
| **Context**                 | 每次处理任务接收的信息总和（临时记忆体），基本单位是 Token                                 |
| **Context Window**          | Context 能容纳的最大 Token 数量                                          |
